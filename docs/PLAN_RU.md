# План развития классического движка — исправленная редакция

Цель: проверить конкурентоспособность с сильными профессиональными игроками в
русские шашки при заранее зафиксированных железе и контроле времени, без таблиц
окончаний. Это проверяемая цель, а не обещание достижения силы к номеру версии.

Эталоны по сообщённым пользователем результатам: v1.7.0 — сила;
v1.9.4 — production foundation. Их прошлые результаты не являются доказательством
корректности нового кода. v1.10.0 — кандидат офлайн-инструментария. Игровые
эвристики и production-параметры не меняются. HCE-v1 с SHA256
709eb59b4858db0dd5d6669583f345dfce8a40ce1d590594c5915a2e217d751f
остаётся экспериментальным; сам файл в приложенном исходном архиве отсутствует.

## Основные исправления исходного плана

1. **Новый seed не делает использованный корпус слепым.** Данные могли уже
   участвовать в TRAIN/DEV, обучении предыдущих поколений или выборе архитектуры.
   FINAL из этого источника обозначается RETROSPECTIVE_NOT_BLIND. Настоящий
   prospective holdout собирается отдельно из ранее не использованных партий
   после фиксации политики и истории происхождения данных. До этого нельзя
   говорить о независимом финальном подтверждении.
2. **Нельзя обещать 3–5 млн уникальных полезных samples заранее.** Это ориентир
   для отчёта, не критерий успешной сборки. Дедупликация, изоляция ролей и фильтры
   могут сильно уменьшить количество. Нельзя ослаблять проверки ради числа.
3. **Нулевые пересечения определяются явно.** Запрещены одинаковые экспортированные
   позиции с одинаковой очередью хода между ролями. Требовать отсутствия общих
   позиций во всех траекториях невозможно: обычные партии начинаются одинаково.
   Позиция старта каждого экспортированного arena opening тоже проходит фильтр;
   промежуточные ходы replay не объявляются независимыми samples.
4. **QRESOLVED не равен случайному продолжению взятий.** Следующий этап должен
   зафиксировать evaluator/search hash, выбор оптимального q-листа, promotion
   budget, ничьи/терминалы, исходную и конечную позиции, путь и очередь хода.
   Результат партии хранится с точки зрения белых; нельзя менять знак только
   потому, что изменился side-to-move. При изменении evaluator фиксированный
   q-лист может устареть: это отдельное приближение, а не точная производная
   текущего qsearch. Stand-pat и терминальные листья не всегда дают обычный
   статический feature vector. В этом релизе QRESOLVED не подделывается.
5. **Teacher не oracle.** Стабильный ход может быть стабильно ошибочным. Нужны
   отдельные стабильные и нестабильные группы; исключение всех трудных позиций
   завышает результат. Top-2/acceptable/regret требуют сопоставимых оценок всех
   нужных корневых альтернатив (а не alpha-beta bounds). PV stability требует
   сохранённого PV. До их реализации эти метрики не выводятся.
6. **Качество на fixed nodes и скорость — разные gates.** Для эквивалентной
   runtime-оптимизации требовать прироста силы при fixed nodes бессмысленно:
   нужна эквивалентность и выигрыш времени. Для tree-changing кандидатов
   заранее задаётся superiority/non-inferiority план; итоговое принятие по
   equal-time. Нейтральный/неопределённый SPRT не означает доказанную равную силу.
7. **Число партий — точность измерения, не обучение во время матча.** Параметры
   заморожены. 1000 партий лучше различают небольшое преимущество, чем 100.
   Много перебираемых кандидатов и повторное использование arena создают
   selection bias: нужна заранее заданная процедура и отдельная confirmation arena.
8. **Pattern, L-BFGS, SMP не обязательны ради списка.** Вводятся по измеренной
   проблеме и ресурсам. v2.0 не обязана включать невыгодный pattern evaluator.
9. **Симметрии сначала доказываются.** Поворот на 180° вместе со сменой цветов
   проверяется дифференциально. Поворот без смены цветов и произвольное отражение
   нельзя автоматически применять к простым шашкам. Side-to-move normalization
   не отменяет направление превращения и знаки целевых величин.
10. **Автоматизация не означает автоматическое принятие незавершённых проверок.**
    Нет данных, бинарника или завершённого gate — кандидат UNVERIFIED/INCOMPLETE,
    а не ACCEPT. Runtime baseline не заменяется из-за лучшего loss.

## Данные и обучение

Источник PDN сохраняется неизменным. Нужны source SHA, версия/хеш экспортёра,
хеш кода сборщика и схемы, seed и параметры выборки. Дубликаты партий определяются
по начальной позиции и семантическим ходам; конфликтующие результаты исключаются.

Выборка стратифицирована по стадии партии, материалу, наличию взятия и превращения.
Длинные партии получают больше возможных samples, но не больший суммарный вес.
Вес пересчитывается после всех удалений. Доли 75/10/5/5/5 — вероятности назначения
партий, не обещанные доли позиций после фильтрации.

Текущая HCE имеет 184 коэффициента, но anchors и нормализация дают зависимые
параметры. Нельзя считать число изменившихся весов мерой полноты обучения.
Integer polish должен работать с допустимыми связанными изменениями (например,
пара PSQT +1/-1), а не ломать нулевые суммы. TRAIN определяет локальное улучшение,
DEV выбирает итоговую модель. FINAL не участвует в оптимизации.

Сначала небольшой pilot для времени и памяти; только затем полный объём.
При 92 i16 признаках один RDTUNE3 sample занимает 246 байт. 3–5 млн samples:
около 738–1230 МБ только бинарных записей, плюс replay и временная SQLite.
Rust-тюнер пока хранит компактные samples в RAM: это не out-of-core optimizer.

## Reference и стоимость

Начинать с 200–1000 позиций, до расширения измерить nodes/s по классам.
250k+1M+4M+16M = 21.25 млн узлов на позицию. Для 20–50 тысяч позиций это
425 млрд–1.0625 трлн узлов, без анализа альтернативных корневых ходов.
Время планируется по реальным измерениям на целевом устройстве.

Teacher замораживается: binary/eval/search/corpus hashes. Каждый бюджет стартует
с чистой TT, иначе «250k против 1M» может означать разные условия прогрева.
Результаты по различным классам и нестабильным позициям сохраняются, а не скрываются.
Совпадение с собственным teacher — диагностическая метрика, не доказательство
силы относительно профессионального игрока.

## Self-play, принятие, внешние матчи

Защищённую ARENA нельзя превращать в источник self-play TRAIN; в исходном плане
это противоречило изоляции данных. Для exploration используются отдельные TRAIN
openings. Для confirmation arena заранее выбирается независимый набор без
подбора удобных дебютов после просмотра результата.

Каждая generation хранит source/binary/config hashes, данные, seed, логи и gates.
accepted pointer обновляется атомарно только после завершённой заранее объявленной
процедуры. Ошибка/прерывание не равны спортивному поражению кандидата.

Внешние матчи: одинаковые правила, TB OFF, фиксированный book policy, аппаратные
условия и контроль времени. Уровень профессионалов подтверждается такими матчами,
а не размером корпуса, loss или сходством архитектуры с другой программой.

## Что именно реализовано в приложенном v1.10.0

- Corpus V2 STATIC и RDTUNE3, SHA-256 манифест, SQLite staging, дедупликация,
  стратифицированный отбор, веса, audit, arena RDOPEN2 compatibility export.
- Reader RDTUNE3 и weighted objective в существующем Adam-тюнере; старый RDTUNE2
  имеет weight=1 и остаётся совместимым. Отдельный запуск с проверкой provenance.
- Reference teacher/benchmark по устойчивости и agreement с replay истории,
  checkpoint/resume, immutable завершёнными запусками.
- Python contract tests и обязательный real-engine integration gate.

В v1.11.0 реализованы QRESOLVED и integer polishing; в v1.11.1 — matched STATIC и общий scale.
Не реализованы: L-BFGS, pattern evaluator,
самогенерация поколений, автоматический promotion, root-alternative regret,
новые time management/SMP. Они остаются этапами выше. Это не реализация всего
плана до v2.0 и не новая доказанно более сильная версия.
