## Первый эксперимент: STATIC + integer polish

Чтобы не смешивать две гипотезы, сначала используйте старый STATIC корпус:

```bash
python3 tools/hce_v2.py \
  --corpus data/corpus_v2 \
  --base config/eval_default.txt \
  --out data/eval/hce_v3_static_polish_01 \
  --epochs 30 --batch 4096 --seed 20260930 \
  --polish-passes 2 --polish-samples 8192
```

При тех же исходных параметрах float-этап должен воспроизвести предыдущий
эксперимент. candidate.continuous.txt — веса до polish; candidate.txt — выбранный
итог. Если целочисленная доводка не улучшила DEV, результат останется прежним.
Polish не обязан изменить веса.

Прогресс: каждые пять секунд сообщение о работе процесса; внутри Rust есть
счётчики загрузки, эпох и доводки. Подробный журнал: training.log.

Polish: детерминированная подвыборка только TRAIN предлагает изменения ±1/±2,
с проекцией bounds, anchors и нулевых сумм PSQT. Это может затронуть соседние
веса в группе PSQT. Целый проход принимается только при снижении ошибки на
ВСЁМ TRAIN и регуляризованной целевой функции. DEV используется для выбора и
остановки после полного прохода, не для подбора координат. L2 совпадает с Adam,
по умолчанию 0.00002; --l2 позволяет явный отдельный эксперимент.

## QRESOLVED на основе готового корпуса

Повторно читать PDN не нужно. Исходный STATIC сохраняется. Учитель для выбора
листа — фиксированный config/eval_default.txt, не обучаемый кандидат.

Сначала ограниченный эксперимент (первые 2000 TRAIN-партий по game_id;
DEV и защищённые роли целиком). Он проверяет время и долю отброшенных позиций,
не предназначен для сравнения силы с полным STATIC:

```bash
python3 tools/qresolved.py \
  --corpus data/corpus_v2 \
  --eval config/eval_default.txt \
  --out data/corpus_qresolved_pilot_01 \
  --node-limit 10000 --max-train-games 2000
```

Для полного корпуса после анализа пилота:

```bash
python3 tools/qresolved.py \
  --corpus data/corpus_v2 \
  --eval config/eval_default.txt \
  --out data/corpus_qresolved_v1 \
  --node-limit 10000
```

Финальный аудит вызывается автоматически. Вывод содержит counts и qresolved_stats:
attempted, nodes, resolved (ДО последующей дедупликации), skip_node_limit,
skip_terminal_or_claim, skip_adjudication, skip_original_role_collision и другие
присутствующие причины. Отсутствующие счётчики равны нулю.

Обучение полного QRESOLVED — отдельный эксперимент. Для первого сравнения
оставьте polish выключенным (default 0), чтобы отделить эффект новых данных:

```bash
python3 tools/hce_v2.py \
  --corpus data/corpus_qresolved_v1 \
  --base config/eval_default.txt \
  --out data/eval/hce_v3_qresolved_01 \
  --epochs 30 --batch 4096 --seed 20260930
```

## Что именно означает QRESOLVED в этом релизе

- Это отдельный capture-only minimax, не производственный qsearch 1:1.
- Все обязательные взятия перебираются существующим генератором, включая
  многоударные ходы, обратные взятия простой и превращение во время взятия.
- Тихие превращения не расширяются. Граница qsearch явно зафиксирована.
- Полная история исходной партии восстанавливается до выбранного полухода.
- При лимите узлов/глубины/истории или неопределённом adjudication вся позиция
  отбрасывается, даже если лимит встретился вне лучшего варианта.
- Терминальный результат и выбранная ничейная претензия не выдаются за статическую
  оценку: такие выбранные листья исключаются. При равенстве со статической
  оценкой предпочтение отдаётся доступной ничейной претензии.
- Для нетерминального листа сохраняются его доска и 92 WHITE-признака. Метка
  результата исходной партии остаётся со стороны белых, независимо от числа
  ходов до листа. qscore — со стороны хода ИСХОДНОЙ позиции, отдельно в provenance.
- TRAIN/DEV преобразуются; REFERENCE/ARENA/FINAL остаются STATIC. Перед преобразованием
  строится индекс исходных позиций всех ролей: лист не может совпасть с исходной
  позицией другой роли. Затем снова удаляются пересечения между новыми листьями.
- Внутри партии одинаковые листья объединяются; веса пересчитываются после
  фильтрации и суммируются в 1 для каждой оставшейся партии.

RDTUNE3 v1 остаётся бинарно совместимым. Режим записан в manifest.json.
Поле ply у Q sample — исходный полуход, а position — лист! Для восстановления
истории Q-листа используйте исходную историю плюс path из q_provenance.jsonl.
Сам q_provenance содержит ВСЕ попытки до окончательной фильтрации, поэтому
resolved_before_final_dedup не гарантирует наличие записи в итоговом RDTUNE3.
Для REFERENCE ply/position по-прежнему описывают одну исходную позицию.

Контрольные суммы фиксируют родительский manifest, бинарник, оценку, инструмент
и параметры. FINAL остаётся retrospective, не новым слепым holdout.
Возобновление Q-сборки не реализовано; Ctrl+C не публикует незавершённый результат.
Повторный запуск требует новой/отсутствующей выходной папки.

## Диагностический отчёт

candidate.diagnostics.csv: split, class, records, weight, base_loss,
candidate_loss, delta, mean_prediction, mean_result, brier.

Группы: all, material/men|mixed|king-heavy, phase/high|middle|low,
tactical/capture|quiet, promotion/true|false, calibration/0..9.
Фаза определяется по material phase evaluator (>=192, >=64, <64), не номеру хода.
Классы пересекаются: нельзя суммировать записи разных осей. Средние взвешенные.
TRAIN-веса внутри тренера нормированы до среднего 1; DEV сохраняет веса корпуса.
Все итоговые Q-листья тихие по взятиям — это ожидаемая особенность отчёта Q.
В legacy RDTUNE2 tactical flags пока неизвестны (нулевые), используйте RDTUNE3.

Сравнивать абсолютные loss между STATIC и QRESOLVED некорректно без учёта
изменения позиций, фильтрации и отдельно fitted scale. Сравнение силы проводим
на прежнем STATIC REFERENCE и той же заранее выбранной арене.
